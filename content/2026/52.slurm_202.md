# Phase 1: Cluster Architecture & The 4 Vital Pillars of HPC

Our local lab consists of **5 containers** connected via an isolated bridge network (`slurm_net`):

+-----------------------------------------------------------------------------------+

### The 4 Vital Pillars of HPC Infrastructure:

Whether deploying Slurm on bare-metal supercomputers, virtual machines, or containerized labs, four architectural requirements must be strictly satisfied:

1. **Shared Munge Cryptographic Key (`/etc/munge/munge.key`):**
   * Munge provides passwordless, ticket-based authentication across distributed daemons. Every node in the cluster (`slurmctld`, `slurmd`, `slurmdbd`, and login nodes) **must share an identical binary key file**.
   * File permissions must be strictly set to **`0400`** (read-only by user `munge`). If permissions are open (`0644` or `0777`), Munge immediately aborts startup for security.
2. **UID / GID Consistency Across Nodes:**
   * Slurm does not use passwords to execute user workloads. When user `kienlt` (UID: `1000`) submits a job from a login node, `slurmctld` dispatches the execution payload to worker node `cnode01`.
   * The `slurmd` daemon on `cnode01` drops root privileges and switches to **UID: 1000**. If user IDs differ between nodes, jobs fail immediately with `Permission Denied`.
3. **Shared POSIX Storage Volume (`/shared`):**
   * Simulates high-performance parallel file systems (NFS, Lustre, BeeGFS). Batch job scripts, datasets, and output logs (`job_%j.out`) must reside on a shared mount path accessible by all nodes.
4. **DNS Resolution & Network Topology:**
   * Nodes must resolve hostnames dynamically (`slurmctld`, `slurmdbd`, `cnode01`, `cnode02`). In Docker Compose, this is handled natively via the internal Docker DNS.

# Phase 2: Level 1 - Deploying the Mini-Cluster with Docker Compose

To optimize memory footprint and build speed, we use a **unified base image** based on Ubuntu 22.04 LTS containing all necessary Slurm binaries.

### 1. Unified Base Image (`Dockerfile`)

```dockerfile
FROM ubuntu:22.04

LABEL maintainer="kienlt"
LABEL description="Lightweight Multi-node Slurm Cluster for Local Lab"

ENV DEBIAN_FRONTEND=noninteractive

# Install Slurm daemons, Munge authentication, MariaDB client, and utilities
RUN apt-get update && apt-get install -y --no-install-recommends \
    bash ca-certificates curl gnupg gosu iputils-ping jq less \
    libmunge-dev libmunge2 mariadb-client munge net-tools netcat-openbsd \
    procps python3 python3-pip slurm-client slurmctld slurmd slurmdbd sudo tree vim \
    && rm -rf /var/lib/apt/lists/*

# Create standard non-root HPC user (UID 1001, GID 1001)
RUN groupadd -g 1001 hpcuser && \
    useradd -m -u 1001 -g 1001 -s /bin/bash hpcuser && \
    echo "hpcuser:hpcuser" | chpasswd && \
    echo "hpcuser ALL=(ALL) NOPASSWD: ALL" >> /etc/sudoers

# Create spool, state, and log directories with appropriate ownership
RUN mkdir -p /var/spool/slurmctld /var/spool/slurmd /var/log/slurm /etc/slurm /shared && \
    chown -R slurm:slurm /var/spool/slurmctld /var/spool/slurmd /var/log/slurm /etc/slurm && \
    chmod 755 /var/spool/slurmctld /var/spool/slurmd /var/log/slurm

COPY entrypoint.sh /usr/local/bin/entrypoint.sh
RUN chmod +x /usr/local/bin/entrypoint.sh

WORKDIR /shared
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["slurmctld"]
```

### 2. Core Configuration (`config/slurm.conf`)

The `slurm.conf` file defines the hardware topology, scheduling logic, and accounting hooks:

```ini
# ===================================================================
# Slurm Configuration File (slurm.conf)
# ===================================================================
ClusterName=homelab
SlurmctldHost=slurmctld

# User & Process Tracking Settings for Containers
SlurmUser=slurm
SlurmctldPort=6817
SlurmdPort=6818
AuthType=auth/munge
CryptoType=crypto/munge
ProctrackType=proctrack/linuxproc
TaskPlugin=task/none
SlurmdParameters=config_overrides
ReturnToService=2

# Runtime State & Log Directories
StateSaveLocation=/var/spool/slurmctld
SlurmdSpoolDir=/var/spool/slurmd
SlurmctldPidFile=/var/spool/slurmctld/slurmctld.pid
SlurmdPidFile=/var/spool/slurmd/slurmd.pid
SlurmctldLogFile=/var/log/slurm/slurmctld.log
SlurmdLogFile=/var/log/slurm/slurmd.log

# Scheduler & Fine-Grained Core/Memory Resource Allocation
SchedulerType=sched/backfill
SelectType=select/cons_tres
SelectTypeParameters=CR_Core_Memory

# Generic Resources (GRES) Configuration
GresTypes=gpu

# SlurmDBD Accounting Hook
AccountingStorageType=accounting_storage/slurmdbd
AccountingStorageHost=slurmdbd
AccountingStoragePort=6819
AccountingStorageUser=slurm
JobAcctGatherType=jobacct_gather/linux
JobAcctGatherFrequency=30

# ===================================================================
# COMPUTE NODES DEFINITION
# ===================================================================
NodeName=cnode01 CPUs=2 RealMemory=1000 State=UNKNOWN
NodeName=cnode02 CPUs=2 RealMemory=1000 Gres=gpu:a100:2 State=UNKNOWN

# ===================================================================
# PARTITIONS DEFINITION
# ===================================================================
PartitionName=cpu Nodes=cnode01 Default=YES MaxTime=INFINITE State=UP
PartitionName=gpu Nodes=cnode02 Default=NO MaxTime=INFINITE State=UP
PartitionName=all Nodes=cnode01,cnode02 Default=NO MaxTime=INFINITE State=UP
```

# Phase 3: Level 2 - Database Accounting & Multi-Tenancy (`sacctmgr`)

In multi-tenant AI labs, compute resources are shared across multiple teams (e.g., NLP Research, Computer Vision, Platform Engineering). Slurm organizes permissions and usage tracking into an **Association Hierarchy**:

```text
                             [ Cluster: homelab ]
                                      │
              ┌───────────────────────┴───────────────────────┐
              ▼                                               ▼
   [ Account: ai-team ]                              [ Account: data-team ]
   (Org: AI-Research)                                (Org: Data-Engineering)
              │                                               │
       ┌──────┴──────┐                                        ▼
       ▼             ▼                                  [ User: bob ]
[ User: kienlt ] [ User: alice ]
```

### Initializing Accounting with `sacctmgr`:

Execute the initialization script once after launching the containers:

```bash
# 1. Register Cluster
sacctmgr -i add cluster homelab

# 2. Create Accounts (Teams / Cost Centers)
sacctmgr -i add account ai-team Description="AI/ML Research Team" Organization="AI-Org"
sacctmgr -i add account data-team Description="Data Engineering Team" Organization="Data-Org"

# 3. Create Users and Bind to Default Accounts
sacctmgr -i add user kienlt DefaultAccount=ai-team AdminLevel=Administrator
sacctmgr -i add user hpcuser DefaultAccount=ai-team

# 4. Verify Association Tree
sacctmgr list association format=Cluster,Account,User,Partition,Share,GrpTRES,MaxJobs
```

### Enforcing Resource Limits & QoS Policies:

Prevent individual engineers or teams from starving the cluster:

```bash
# Limit user alice to a maximum of 5 concurrent running jobs:
sacctmgr modify user alice set MaxJobs=5

# Restrict the entire ai-team to a maximum of 8 concurrent GPUs:
sacctmgr modify account ai-team set GrpTRES=gres/gpu=8
```

# Phase 4: Level 3 - GPU Cluster Simulation via Generic Resources (GRES)

How can you practice writing GPU submission scripts, test `--gres=gpu:1`, and verify `$CUDA_VISIBLE_DEVICES` injection when your local machine **lacks dedicated NVIDIA hardware**?

👉 **Solution:** Use Slurm's **Dummy Generic Resources (GRES)** mechanism!

### 1. Creating Character Device Nodes in `entrypoint.sh`

When container `cnode02` boots with `privileged: true`, we dynamically create two character device nodes:

```bash
mknod -m 666 /dev/nvidia0 c 195 0 2>/dev/null || true
mknod -m 666 /dev/nvidia1 c 195 1 2>/dev/null || true
```

### 2. Mapping in `config/gres.conf`

Declare these character devices as two simulated NVIDIA A100 GPUs:

```ini
# ===================================================================
# Generic Resources (GRES) Configuration (gres.conf)
# ===================================================================
NodeName=cnode02 Name=gpu Type=a100 File=/dev/nvidia[0-1]
```

### 3. Verifying Automatic Environment Injection:

Request 1 GPU:
```bash
srun -p gpu --gres=gpu:1 bash -c 'echo "Allocated Node: $(hostname), CUDA_VISIBLE_DEVICES: $CUDA_VISIBLE_DEVICES"'
```
Output:
```text
Allocated Node: cnode02, CUDA_VISIBLE_DEVICES: 0
```

Request 2 GPUs:
```bash
srun -p gpu --gres=gpu:2 bash -c 'echo "Allocated Node: $(hostname), CUDA_VISIBLE_DEVICES: $CUDA_VISIBLE_DEVICES"'
```
Output:
```text
Allocated Node: cnode02, CUDA_VISIBLE_DEVICES: 0,1
```

Slurm automatically tracks available GPU slots, enforces device locking, and injects the corresponding environment variables into the job context seamlessly!

# Phase 5: Turning Your Host Machine into a Native Login Node

In real production environments, engineers never execute `docker exec` into the controller. You can configure **your physical host PC** as a native Slurm Login Node, enabling you to run `sinfo`, `squeue`, and `sbatch` directly from your regular terminal!

```text
[ Your Physical Host Terminal ]
  • Commands: sinfo, squeue, sbatch
  • Local Config: /etc/slurm/slurm.conf & /etc/munge/munge.key
                 │
                 │ Direct RPC to localhost:6817
                 ▼
[ 5-Container Slurm Cluster ]
```

### 3-Step Setup:

#### Step 1: Install Client Packages on Host
```bash
sudo apt update && sudo apt install -y slurm-client munge
```

#### Step 2: Synchronize Munge Key & Slurm Configuration
```bash
# Copy cryptographic key and enforce 0400 permissions
sudo cp config/munge.key /etc/munge/munge.key
sudo chown munge:munge /etc/munge/munge.key
sudo chmod 400 /etc/munge/munge.key
sudo systemctl restart munge

# Copy cluster configuration
sudo mkdir -p /etc/slurm
sudo cp config/slurm.conf /etc/slurm/slurm.conf
```

#### Step 3: Add DNS Resolution to `/etc/hosts`
```bash
grep -q "slurmctld" /etc/hosts || echo "127.0.0.1 slurmctld slurmdbd" | sudo tee -a /etc/hosts
```

You can now open any terminal window on your host OS and interact directly with the cluster!

# Phase 6: Essential Slurm CLI Toolkit & Workflow

The Slurm CLI ecosystem is structured into **5 operational domains**:

```text
                                 [ SLURM CLI TOOLKIT ]
                                           │
  ┌───────────────────┬────────────────────┼───────────────────┬───────────────────┐
  ▼                   ▼                    ▼                   ▼                   ▼
[ Cluster & Nodes ] [ Job Execution ]    [ Active Queue ]    [ Accounting ]      [ Administration ]
• sinfo             • sbatch             • squeue            • sacct             • scontrol
• salloc            • srun               • scancel           • sstat             • sacctmgr
                                                             • sreport
```

### 1. `sinfo` - Cluster & Node Inspection
```bash
# Default cluster overview
sinfo

# Node-by-node hardware specification view
sinfo -N -l

# View outage reasons for offline nodes
sinfo -R
```

* **Node State Matrix (`STATE`):**
  * `idle`: Fully available and healthy.
  * `alloc`: 100% of CPUs/GPUs are currently allocated.
  * `mix`: Partially busy; some CPUs/RAM are still free.
  * `drain`: Administratively disabled for maintenance (runs existing jobs to completion).

### 2. `squeue` - Active Scheduling Queue
```bash
# View active queue
squeue

# Filter by user
squeue -u $USER

# Continuous live streaming (refresh every 2 seconds)
squeue -i 2
```

* **Diagnosing Pending Reasons (`NODELIST(REASON)`):**
  * `(Resources)`: Waiting for busy CPUs/GPUs to become free.
  * `(Priority)`: Higher-priority jobs are ahead in the backfill queue.
  * `(ReqNodeNotAvail)`: Target hardware or partition is offline (`DRAIN` / `DOWN`).
  * `(Dependency)`: Waiting for a prerequisite job to complete (`--dependency`).

### 3. `sbatch` - Asynchronous Batch Job Submission
Create `train.sh`:
```bash
#!/usr/bin/env bash
#SBATCH --job-name=bert_finetune
#SBATCH --partition=gpu
#SBATCH --nodes=1
#SBATCH --gres=gpu:a100:1
#SBATCH --time=02:00:00
#SBATCH --output=/shared/job_%j.out
#SBATCH --error=/shared/job_%j.err

echo "Starting training job ${SLURM_JOB_ID} on $(hostname)..."
echo "Assigned GPU device: ${CUDA_VISIBLE_DEVICES}"
python3 -c "import time; print('Training neural network...'); time.sleep(10)"
```
Submit to the cluster:
```bash
sbatch train.sh
# Output: Submitted batch job 105
```

### 4. `srun` - Interactive Execution & Debugging
```bash
# Parallel execution across all nodes simultaneously
srun -p all -N 2 hostname

# Launch an interactive PTY Bash session on a GPU compute node for debugging
srun -p gpu --gres=gpu:1 --pty bash -i
```

### 5. `scancel` - Job Cancellation & Signal Handling
Locate the Job ID from the `sbatch` return message or `squeue`:
```bash
# Cancel a specific job:
scancel 105

# Cancel ALL jobs submitted by user:
scancel -u $USER

# Cancel only PENDING jobs in queue (leave running jobs untouched):
scancel -u $USER -t PENDING

# Send graceful checkpointing signal before stopping:
scancel --signal=SIGUSR1 105
```

### 6. `sacct` & `sstat` - Historical Auditing & Memory Profiling
```bash
# Query historical jobs, exit codes, and peak memory usage (MaxRSS):
sacct --format=JobID,JobName,Partition,State,ExitCode,Elapsed,MaxRSS

# Real-time memory profiling of active running jobs (leak detection):
sstat -j 105.batch --format=JobID,MaxRSS,AveCPU,AveDiskRead
```

# Phase 7: Battle-Tested Troubleshooting & War Stories

Building containerized Slurm clusters often triggers subtle edge cases. Below are 5 real-world debugging lessons encountered during development:

```text
+-----------------------------------------------------------------------------------+
|                        SLURM OPERATIONAL TROUBLESHOOTING                          |
+------------------------------------+----------------------------------------------+
| Symptom / Log Error                | Root Cause & Resolution                      |
+------------------------------------+----------------------------------------------+
| unpack_header: protocol_version    | ❌ Version mismatch between client & server. |
| not supported (Zero Bytes)         | ✅ Sync Slurm versions (e.g., both v21.08).  |
+------------------------------------+----------------------------------------------+
| cgroup_dbus_attach_to_scope:       | ❌ Slurm v23+ attempts systemd D-Bus connect.|
| cannot connect to dbus daemon      | ✅ Use ProctrackType=proctrack/linuxproc.    |
+------------------------------------+----------------------------------------------+
| Node configuration differs         | ❌ Host physical CPUs differ from config.    |
| from hardware (CPUs=2:24)          | ✅ Enable SlurmdParameters=config_overrides. |
+------------------------------------+----------------------------------------------+
| Invalid GRES record: duplicate     | ❌ Duplicate GPU device paths (/dev/null).   |
| device file name (/dev/null)       | ✅ Use mknod for distinct /dev/nvidia[0-1].  |
+------------------------------------+----------------------------------------------+
| Can not recover assoc_usage        | ❌ State file binary format from newer Slurm.|
| state, incompatible version        | ✅ Wipe state volume (docker compose down -v)|
+------------------------------------+----------------------------------------------+
```
