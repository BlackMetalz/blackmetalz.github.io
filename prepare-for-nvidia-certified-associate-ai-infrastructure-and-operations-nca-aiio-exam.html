4. Official Exam Blueprint & Domain Weights

According to NVIDIA's official exam specifications, the certification is divided into 3 core weighted domains:

  • Essential AI Knowledge
  • AI Infrastructure
  • AI Operations

Domain 1: Essential AI Knowledge (38% of Exam)

This domain validates foundational understanding of accelerated computing concepts, AI workload lifecycles, and the NVIDIA software ecosystem.

1.1 CPU vs. GPU vs. DPU Architecture:

  • CPU (Latency-Optimized): Few powerful cores with large caches designed for sequential processing and branch prediction.
  • GPU (Throughput-Optimized): Thousands of smaller, energy-efficient cores designed for massive parallel matrix operations (SIMD/SIMT).
  • DPU (Data Processing Unit - BlueField): Offloads, accelerates, and isolates data center infrastructure workloads (networking, security, telemetry, storage virtualization) away from host CPUs/GPUs.

1.2 AI Workflow Lifecycle:

  • Data Ingestion & Preprocessing: High I/O throughput, traditionally CPU/RAM intensive. Can be GPU-accelerated with RAPIDS (cuDF, cuML) and DALI (data loading/augmentation).
  • Model Training: Compute and inter-GPU bandwidth intensive. Utilizes mixed precision (FP32 master weights + TF32/FP16/BF16/FP8 compute).
  • Model Fine-Tuning: LoRA, QLoRA, full parameter fine-tuning.
  • Inference & Serving: Low-latency, high-throughput token generation. Optimized with quantization (INT8, FP4) and KV-caching.

1.3 NVIDIA Full-Stack AI Ecosystem & Software:

                                   │

  • CUDA (Compute Unified Device Architecture): Parallel computing platform and programming model for NVIDIA GPUs.
  • cuDNN: Highly tuned primitives for deep neural networks (convolutions, pooling, normalization, activation).
  • NCCL (NVIDIA Collective Communications Library): Multi-GPU and multi-node collective communication primitives (AllReduce, AllGather, Broadcast, ReduceScatter) optimized for NVLink and InfiniBand.
  • TensorRT: High-performance deep learning inference optimizer and runtime (layer fusion, kernel auto-tuning, quantization).
  • TensorRT-LLM: Open-source library for optimizing LLM inference on NVIDIA GPUs (in-flight batching, paged KV-cache, FP8/FP4 quantization).
  • Triton Inference Server (now branded NVIDIA Dynamo Triton): Multi-framework open-source model serving software (PyTorch, ONNX, TensorRT, vLLM, Python backend) supporting concurrent model execution, dynamic batching, and model pipelining. TensorRT optimizes the model; Triton serves it.
  • DOCA: SDK for programming BlueField DPUs / SuperNICs (networking, security, storage offload).
  • NVIDIA NeMo: End-to-end cloud-native framework for building, customizing, and training generative AI models.
  • NVIDIA AI Enterprise (NVAIE): Enterprise platform providing production support, validated container images, security patches, and microservices (NVIDIA NIM).
  • NGC (NVIDIA GPU Cloud) Registry: Curated catalog of GPU-optimized containers, pre-trained model weights, Helm charts, and SDKs.

Domain 2: AI Infrastructure (40% of Exam)

The largest domain in the exam covers GPU hardware architectures, interconnects, high-speed networking fabrics, and storage pipelines.

2.1 GPU Architectural Generations:

  • Ampere (A100): Introduced 3rd Gen Tensor Cores, TF32 precision, BF16 support, Multi-Instance GPU (MIG), and NVLink 3 (600 GB/s bidirectional).
  • Hopper (H100 / H200): Introduced Transformer Engine (FP8 precision), DPX instructions for dynamic programming, confidential computing, and NVLink 4 (900 GB/s bidirectional). H200 = H100 compute with 141GB HBM3e.
  • Blackwell (B200 / GB200): 2nd Gen Transformer Engine (FP4 precision), 208 billion transistors, NVLink 5 (1.8 TB/s bidirectional), NVLink Switch Chip.
    • GB200 Superchip = 1 Grace CPU + 2 Blackwell GPUs connected via NVLink-C2C.
    • GB200 NVL72 = 36 Grace CPUs + 72 Blackwell GPUs in a single NVLink domain (liquid-cooled rack).

Key points to remember:

  • H100 vs. A100: Same max memory size (80GB) but faster HBM3, 1.5x NVLink bandwidth (900 vs. 600 GB/s), FP8 via Transformer Engine.
  • H200 = H100 + more/faster memory: Same Hopper compute, but 141GB HBM3e (~1.8x capacity, ~1.4x memory bandwidth). Best for large-model inference and long context. Drop-in compatible with HGX H100 systems.
  • B100: Lower-power Blackwell (700W, same as H100), HGX B100 boards are drop-in compatible with HGX H100 (no new power/cooling needed). In practice, NVIDIA ships mainly B200 / GB200.
  • B200: 180GB HBM3e (NVIDIA docs; early launch material said 192GB, and DGX B200 = 8 × 180 = 1,440GB), 1000W (liquid cooling recommended at scale), FP4, 2x NVLink bandwidth vs. H100. New Blackwell features: RAS Engine (reliability/predictive maintenance), confidential computing, decompression engine (accelerates data analytics).
  • Grace CPU (in GB200 / GH200): 72 Arm Neoverse V2 cores, LPDDR5X memory, connected to GPUs via NVLink-C2C (900 GB/s), 7x faster than PCIe Gen5.
  • Other GPUs that may appear: L40S (Ada Lovelace, 48GB GDDR6, no NVLink, for inference/graphics/Omniverse), L4 (Ada, 24GB, low-power 72W inference/video), GH200 (Grace Hopper Superchip = 1 Grace + 1 H100/H200).

Sources: NVIDIA H200, DGX B200 User Guide, Inside NVIDIA Blackwell Ultra (B200: 208B transistors, 180GB HBM3e).

DGX Hardware Details (common "how many X in a DGX" questions):

DGX A100 (6U):

  • GPU: 8× A100, connected by 6 NVSwitch chips (600 GB/s per GPU).
  • CPU: 2× AMD EPYC 7742 (Rome), 64 cores each = 128 cores total.
  • System memory: 1TB (320GB model) / 2TB (640GB model).
  • Compute networking: 8× single-port Mellanox ConnectX-6 VPI (200Gb/s HDR InfiniBand) — 1 NIC per GPU.
  • Storage / in-band networking: 1× dual-port ConnectX-6 VPI (10/25/50/100/200Gb/s Ethernet by default), 2× on the 640GB model.
  • Storage: OS on 2× 1.92TB M.2 NVMe; internal cache 15TB (4× 3.84TB U.2 NVMe), 30TB on the 640GB model.

DGX H100 (8U) — DGX H200 is the same chassis with H200 GPUs:

  • GPU: 8× H100, connected by 4 NVSwitch chips (900 GB/s per GPU).
  • CPU: 2× Intel Xeon Platinum 8480C (Sapphire Rapids), 56 cores each = 112 cores total.
  • System memory: 2TB.
  • Compute networking: 8× single-port ConnectX-7 VPI (400Gb/s NDR InfiniBand/Ethernet), exposed through 4 twin-port OSFP cages (800G each).
  • Storage / in-band networking: 2× dual-port BlueField-3 DPU (up to 400Gb/s, QSFP112).
  • Storage: OS on 2× 1.92TB M.2 NVMe (RAID 1); data cache ~30TB (8× 3.84TB U.2 NVMe, RAID 0).
  • Power: 6× 3.3kW PSUs, ~10.2 kW max.

DGX B200 (10U):

  • GPU: 8× B200 (1,440GB total), connected by 2 NVLink 5 switch chips (1.8 TB/s per GPU, 14.4 TB/s aggregate).
  • CPU: 2× Intel Xeon Platinum 8570, 112 cores total.
  • System memory: 2TB (configurable to 4TB).
  • Networking: Same pattern as DGX H100: 8× ConnectX-7 400Gb/s (4 OSFP ports) for compute + 2× dual-port BlueField-3 DPU for storage/in-band.
  • Storage: OS on 2× 1.92TB M.2 NVMe (RAID 1); data cache 8× 3.84TB U.2 NVMe (RAID 0).
  • Power: 6× 3.3kW PSUs, ~14.3 kW max.

Rule of thumb: 1 compute NIC per GPU (8 GPUs → 8 compute NICs, "rail-optimized" design), and a separate NIC/DPU pair for storage and in-band management. On top of that, every DGX has a dedicated BMC (RJ45) port for out-of-band management.

NVIDIA headline performance claims (often used in exam questions):

  • DGX B200 vs. DGX H100: up to 3x training and 15x LLM inference performance.
  • GB200 NVL72 vs. H100: up to 30x faster real-time trillion-parameter LLM inference, 4x faster training, 25x better energy efficiency (TCO).

Note: Spec numbers above were cross-checked (Sep 2026) against the official DGX A100 Datasheet, DGX H100/H200 User Guide, DGX B200 User Guide, DGX B200 product page, GB200 NVL72 product page and DGX GB200 Hardware Guide. NVIDIA updates these pages over time, so re-check before your exam.

2.2 NVIDIA System Platforms: DGX vs. HGX vs. MGX:

  • DGX: NVIDIA's complete, turnkey AI system (hardware + software stack), e.g., DGX H100/B200. Scales to DGX SuperPOD (reference architecture).
  • HGX: GPU baseboard (8 GPUs + NVSwitch) sold to OEMs (Dell, HPE, Supermicro...) to build their own servers.
  • MGX: Modular reference server architecture for OEMs to build many server configurations (CPU, GPU, DPU combinations).

2.3 Tensor Cores & Precision Formats:

  • Matrix Acceleration: Tensor Cores are specialized cores that accelerate the matrix multiply-and-add operations at the heart of deep learning: D = A × B + C.
  • FP32: Single precision (1 sign, 8 exponent, 23 mantissa bits). Standard scientific computing, master weights.
  • TF32 (TensorFloat-32): Same range as FP32 (8-bit exponent), same precision as FP16 (10-bit mantissa). Internal compute format only (not a storage format), used by Ampere+ math libraries. Note: PyTorch disabled TF32 for matmul by default since v1.12 (still on for cuDNN convolutions).
  • BF16 (bfloat16): 1 sign, 8 exponent, 7 mantissa bits. Same range as FP32, no loss scaling needed. Ampere+. The de facto standard for LLM training today.
  • FP16: 1 sign, 5 exponent, 10 mantissa bits. Narrow range, requires loss scaling to avoid gradient underflow. Classic mixed precision on Volta/Turing.
  • FP8 (E4M3 / E5M2): Hopper/Blackwell via Transformer Engine. E4M3 (more precision) for forward pass (weights/activations), E5M2 (more range) for backward pass (gradients).
  • INT8 / FP4 (NVFP4 on Blackwell): Quantized inference with small accuracy loss, lower memory and higher throughput.

2.4 High-Speed Interconnects: NVLink & NVSwitch:

  • PCIe Limitation: Standard PCIe Gen5 x16 provides ~64 GB/s per direction (~128 GB/s bidirectional), creating a major communication bottleneck for multi-GPU training. NVLink 4 (900 GB/s) is ~7x PCIe Gen5.
  • NVLink: Direct high-speed interconnect between GPUs bypassing the PCIe bus (H100: 18 links × 50 GB/s = 900 GB/s).
  • NVSwitch: Non-blocking switch chip enabling any-to-any full-bandwidth GPU communication within a node (e.g., all 8 GPUs in a DGX H100 talk to each other simultaneously at full NVLink speed via 4 NVSwitch chips; DGX A100 uses 6).
  • NVLink Switch (Blackwell): Extends NVLink beyond a single server to form rack-scale NVLink domains (e.g., 72 GPUs in GB200 NVL72).

2.5 GPU Sharing: MIG vs. vGPU vs. Time-Slicing:

  • Multi-Instance GPU (MIG): Partitions a single physical GPU (A100/H100/H200/B200) into up to 7 isolated GPU instances (A30: up to 4).
    • Each instance has dedicated hardware resources: compute cores, high-bandwidth memory, cache, and memory bandwidth (true hardware QoS and fault isolation).
  • NVIDIA vGPU (Virtual GPU): Software (hypervisor-level) sharing of GPUs across virtual machines (VMware, KVM...). Requires vGPU license. Can be combined with MIG.
  • Time-Slicing: GPU is shared by multiple processes/containers taking turns. No memory or fault isolation (common in Kubernetes for light workloads).

2.6 AI Data Center Networking & Fabrics:

Remember this shit, 4 distinct network fabrics.

                    THE 4 DATA CENTER NETWORK FABRICS
                                   │
  ┌─────────────────┬──────────────┴──────────────┬─────────────────┐
  ▼                 ▼                             ▼                 ▼
[ Compute Fabric ] [ Storage Fabric ]       [ In-Band Mgmt ]  [ Out-of-Band (OOB) ]
• InfiniBand /     • InfiniBand / RoCE      • Node telemetry  • IPMI, BMC
  Spectrum-X       • Parallel storage access• SSH, cluster API• Dedicated 1GbE
• Inter-node NCCL    (Weka, Lustre, VAST)
  1. Compute (East-West) Fabric: Connects GPUs across different server nodes for distributed training (AllReduce collective operations). Uses InfiniBand (Quantum-2 400Gb/s, Quantum-X800 800Gb/s) or Spectrum-X Ethernet.
  2. Storage Fabric: Connects compute nodes to high-speed shared parallel storage systems (Lustre, Weka, VAST Data) over InfiniBand or RoCE Ethernet (NVMe-oF).
  3. In-Band Management Fabric: Cluster communication, job scheduling, API requests, and user traffic.

  4. Out-of-Band (OOB) Management Fabric: Dedicated physical network connecting server BMC/IPMI controllers for power control and bare-metal provisioning.

  5. RDMA (Remote Direct Memory Access): Bypasses the operating system kernel and remote CPU (zero-copy), allowing a network adapter to read/write the host memory of a remote machine directly.

  6. GPUDirect RDMA: Extends RDMA so the NIC reads/writes GPU memory directly, without staging through host RAM. This is what NCCL uses for fast inter-node GPU communication.
  7. InfiniBand: Native hardware-based credit-based flow control (lossless), very low latency, adaptive routing, and In-Network Computing (SHARP - Scalable Hierarchical Aggregation and Reduction Protocol). Managed by a Subnet Manager (UFM).
  8. RoCE (RDMA over Converged Ethernet): RoCEv1 works at Ethernet L2 only; RoCEv2 encapsulates the InfiniBand transport header inside UDP/IP (port 4791), making it routable. Requires lossless/congestion-controlled Ethernet (PFC - Priority Flow Control, ECN - Explicit Congestion Notification, combined as DCQCN).
  9. NVIDIA Spectrum-X: Ethernet platform designed specifically for generative AI clouds (Spectrum-4 switches + BlueField-3 SuperNICs), delivering near-InfiniBand performance over Ethernet.

2.7 AI Storage Architecture & GPUDirect Storage (GDS):

  • Traditional I/O copies data from NVMe disk -> CPU Memory (page cache) -> Bounce Buffer (also in CPU memory) -> GPU Memory (VRAM), consuming CPU cycles and PCIe bandwidth.
  • GPUDirect Storage (GDS): Enables a direct memory access (DMA) path between storage and GPU VRAM, skipping the CPU bounce buffer. Local NVMe uses PCIe peer-to-peer; remote storage (NVMe-oF, parallel file systems) uses RDMA. Result: lower latency, higher throughput, and lower CPU utilization. Applications use the cuFile API (kernel module nvidia-fs).
Traditional Path:
Storage/NIC ──► Host RAM (CPU Buffer) ──► Host RAM (Bounce) ──► GPU Memory

GPUDirect Storage (GDS) Path:
Storage/NIC ─────────────────(Direct PCIe / RDMA)───────────────► GPU Memory
  • Parallel File Systems: AI architectures utilize parallel file systems (Lustre / DDN EXAScaler, WEKA, VAST Data, IBM Storage Scale (formerly Spectrum Scale), BeeGFS) to serve many concurrent clients with high throughput and scalable metadata.
  • Storage tiers: Local NVMe (fast cache/scratch) -> shared parallel file system (training datasets, checkpoints) -> object storage (long-term data lake).

2.8 Power, Cooling & Data Center Considerations:

  • Power density: AI racks draw far more power than traditional racks (DGX H100 ~10.2 kW per system; GB200 NVL72 ~120 kW per rack), so power and cooling capacity must be planned up front.
  • Air cooling vs. liquid cooling: Air cooling hits its limit at high rack density. Direct-to-chip liquid cooling (cold plates) removes heat much more efficiently and is required for GB200 NVL72.
  • PUE (Power Usage Effectiveness): Total facility power / IT equipment power. Closer to 1.0 = more efficient.
  • Other factors: Redundant power (N+1, 2N), hot/cold aisle containment, floor weight, and cabling for high-speed fabrics.
  • On-prem vs. Cloud vs. Hybrid: On-prem gives control and lower long-term cost at high utilization; cloud gives elasticity and fast start with no CapEx; hybrid mixes both.

Domain 3: AI Operations (22% of Exam)

This domain covers workload scheduling, cluster orchestration, provisioning, and health telemetry.

3.1 Workload Schedulers: Slurm vs. Kubernetes:

  • Slurm: The standard for large-scale distributed AI pre-training. Native support for multi-node MPI, network topology awareness (topology/tree), all-or-nothing multi-node allocation, and tight consumable resource tracking (cons_tres, GRES for GPUs). Note: in Slurm terminology, "gang scheduling" means time-slicing jobs (PreemptMode=GANG), not all-or-nothing allocation.
  • Kubernetes + NVIDIA GPU Operator: The standard for microservices, inference serving, and enterprise pipelines. The GPU Operator automates the deployment of:
    • NVIDIA driver and NVIDIA Container Toolkit
    • Kubernetes device plugin (exposes nvidia.com/gpu resource)
    • GPU Feature Discovery (labels nodes with GPU properties) and Node Feature Discovery
    • MIG Manager
    • DCGM / DCGM Exporter (monitoring)
    • Operator validator
  • NVIDIA Network Operator: Companion operator that deploys networking components (MOFED/DOCA drivers, RDMA shared device plugin, GPUDirect RDMA) on K8s nodes.

3.2 NVIDIA Base Command Manager (BCM):

  • Cluster management and provisioning software (formerly Bright Cluster Manager) for DGX and non-DGX clusters. Automates bare-metal OS provisioning, InfiniBand fabric health checks, monitoring, and workload scheduler integration (Slurm, Kubernetes).
  • Do not confuse with NVIDIA Base Command Platform (a SaaS for managing AI training workloads on DGX Cloud).

3.3 Monitoring & Telemetry (nvidia-smi & DCGM):

  • nvidia-smi: CLI for checking a single node: GPU utilization, memory usage, temperature, power, running processes, ECC errors, MIG configuration (nvidia-smi mig), topology (nvidia-smi topo -m).
  • NVIDIA DCGM (Data Center GPU Manager): Low-overhead daemon (nv-hostengine) that collects GPU telemetry across the cluster (temperature, power draw, GPU utilization, memory utilization, PCIe bandwidth, NVLink bandwidth, ECC memory errors, XID errors).
    • Health checks & policies: Background health monitoring and automated actions on events.
    • Diagnostics: dcgmi diag -r 1|2|3|4 (from quick checks to long stress tests).
  • Exposes metrics via NVIDIA DCGM Exporter to Prometheus, for Grafana dashboards and automated alerting.
  • XID errors: Error codes reported by the NVIDIA driver in the kernel log (dmesg), used to diagnose GPU hardware/driver issues.

5. Other Things to Remember

  • NVIDIA Merlin is a scalable and GPU-accelerated solution, making it easy to build recommender systems.
  • Apptainer is not orchestration, it is containerization (like Docker), usually used in HPC.
  • When we talking about optimize communication and transfer data between multi-GPU in same or multi-node, remember NCCL.
  • NVIDIA NIM is a set of accelerated inference microservices that allow organizations to run AI models on NVIDIA GPUs anywhere.
  • OpenSM (Open Subnet Manager) is an InfiniBand specification-based subnet manager and administrator that configures the InfiniBand fabric
  • LLM foundation: Transformer model (read more about Attention is what you need). Transformer like a car and Attention is engine.
  • ConnectX-6 supports two ports of 200Gb/s Ethernet connectivity.

6. Study Plan & Quick Review Checklist

Before sitting for the exam, ensure you can confidently answer the following checklist:

  • Explain why GPUs are faster than CPUs for matrix operations.
  • Differentiate between InfiniBand and Ethernet, and explain what RDMA achieves.
  • Explain the role of NVLink and NVSwitch inside an 8-GPU node.
  • Describe how Multi-Instance GPU (MIG) provides hardware-level QoS, and how it differs from vGPU and time-slicing.
  • Differentiate FP16, BF16, TF32 and FP8 (E4M3 vs. E5M2).
  • Explain the difference between RDMA and GPUDirect RDMA.
  • Explain how GPUDirect Storage (GDS) eliminates CPU memory bounce buffers.
  • Differentiate DGX, HGX and MGX.
  • Explain why high-density AI racks need liquid cooling, and what PUE measures.
  • List the 4 network fabrics in an AI data center and identify their functions.
  • Explain the purpose of NCCL in distributed multi-GPU training.
  • Identify the differences between Triton Inference Server and TensorRT.
  • Explain what the NVIDIA GPU Operator deploys on a Kubernetes cluster.
  • Describe what DCGM monitors and how it integrates with Prometheus.
